## この資料の使い方

このガイドは、公式コースと工程表の学習分野に対応させた独自教材です。公式教材の全文翻訳、公式問題集、公式認定教材ではありません。各章は「日本語で理解する→公式の該当単元を見る→操作する→説明する」の順で使います。公式コースとは学習順を一部組み替え、工程表の順を優先しています。

初週の基礎演習は手順を詳しく書き、後半は概念・演習課題・判断基準をまとめています。後半の操作場所はインストールしたStudioとアクティビティパッケージの版で異なるため、公式の該当単元を併用してください。この資料だけで全範囲の詳細操作や試験問題を網羅したとは扱いません。

PlaywrightやSeleniumの経験は、要素指定・待機・例外・再実行の理解に活かせます。UiPathでは、その考え方をアクティビティとワークフローに置き換えて学びます。

コード例はVB.NET式です。演習はVBを選んだWindowsプロジェクトを基準にします。C#プロジェクトでは同じ式をそのまま使わず、対応するC#式に直してください。日本語訳は理解の補助です。画面上の名称は英語も確認します。

毎日の目安は実作業5時間です。日本語理解45分、公式単元60分、実習120分、確認とGit保存45分、振り返り30分。休憩は別に取り、分からない英語は該当箇所に絞って調べます。

## 1章　環境と最初の実行〔T01〕

### 理解する

Studioはワークフローを作る道具です。アクティビティ（Activity）は「文字を表示する」「ファイルを読む」など一つの処理部品で、ワークフロー（Workflow）はそれらをつないだ処理です。プロジェクトにはXAMLファイル、設定、依存パッケージなどが含まれます。

### 操作演習

1. 公式の案内から利用できる無料環境を準備し、Studioの版・ライセンス・パッケージ版をメモする。機能の提供状況はアカウントごとに確認する。
2. Windows・VBのProcessプロジェクトを作る。名称は `AssociateBasics` とする。
3. MainにSequence（順次処理）を配置する。テンプレートに既にある場合はその中を使う。
4. Write Line（行を書き込み）を追加し、Textに `"学習を開始します"` を入力する。文字列は引用符で囲む。
5. 実行し、Output（出力）で文字を確認する。保存後にStudioを閉じ、開き直してもう一度実行する。
6. READMEに起動方法と期待出力を書く。生成ファイルのうち不要なキャッシュや秘密情報をGitに入れない。

**確認：**「ActivityとWorkflowはどう違う？」  
**解説：**前者は処理部品、後者は部品を組み合わせた処理全体。  
**完了：**新しく開き直して実行でき、使用版と期待出力を記録した。

## 2章　RPAと製品の役割〔T02〕

RPAは、決めた手順に従うPC作業を自動化する方法です。作業頻度が高く、入力が整理され、判断ルールが明確な処理を候補にします。例外の多い業務をそのまま自動化するより、入力と判断を先に整理します。

| 用語 | 役割 | 混同しやすい点 |
|---|---|---|
| Studio | 処理を開発・デバッグする | 実行の集中管理とは別 |
| Robot | 作った処理を実行する | 開発画面そのものではない |
| Orchestrator | 配布・実行・資源・監視などを管理する | 個々の画面操作はワークフロー側で定義 |
| Attended | 人の操作に関わる実行形態 | 「実行中ずっと人がクリックする」の意味ではない |
| Unattended | 人の介入を前提としない実行形態 | ライセンス・実行環境・権限などの準備が必要 |

**演習：**「毎月のCSV集計」「自由文の苦情の最終判断」を候補として、ルールの明確さ・例外・誤処理時の影響を比較する。自動化する部分と人が確認する部分を書く。

**確認：**「Studioで作った処理の実行履歴や配布をまとめて扱う製品は？」  
**解説：**Orchestrator。開発、実行、管理の役割を分けて説明する。  
**完了：**3製品の役割と、業務候補を選ぶ理由を自分の言葉で説明できる。

## 3章　変数・型・スコープ・引数〔T03〕

変数（Variable）は処理中の値を置く場所です。Stringは文字、Int32は整数、Booleanは真偽を表します。型（Type）が違う値を扱うときは、変換できるか確認します。Scopeは変数を使える範囲です。子の処理では親のスコープの値を使えますが、子だけに作った変数は親や兄弟から直接使えません。

引数（Argument）はワークフロー間で値を渡す入口・出口です。

| 方向 | 用途 | 例 |
|---|---|---|
| In | 呼び出し先へ渡す | 税抜金額を渡す |
| Out | 呼び出し先から返す | 計算結果を返す |
| In/Out | 受け取って更新値を返す | 受け取ったカウンターを増やす |

### 演習A：値と型

1. Sequenceに `userName`（String）、`count`（Int32）、`isReady`（Boolean）を作る。
2. Assignで順に `"Akihito"`、`3`、`True` を代入する。
3. Write Lineに `userName & " : " & count.ToString()` を指定する。期待出力は `Akihito : 3`。
4. countを5に変え、結果が変わることを確認する。
5. 別の子Sequenceだけに変数を作り、外から参照できないことを検証する。検証後はエラーを解消する。

### 演習B：ワークフロー間で値を渡す

1. `CalculateAmount.xaml` を作り、In引数 `in_Amount`（Decimal）とOut引数 `out_Total`（Decimal）を定義する。
2. Assignで `out_Total = in_Amount * 1.1D` とする。これは計算練習であり、実際の税計算の端数規則は別に必要。
3. MainにDecimal変数 `total` を作る。Invoke Workflow Fileで子を呼び、in_Amountに `1000D`、out_Totalに `total` を対応させる。
4. Write Lineで `total.ToString()` を出す。数値として1100になることを確認する。表示の小数桁は環境による。
5. 入力を2000に変え、2200になることを確認する。

**確認：**「結果だけを子から返す引数の方向は？」  
**解説：**Out。変数のスコープを広げるだけでは、別XAMLへの受け渡しの設計にはならない。  
**完了：**入力を変えて再現でき、型・スコープ・引数方向を説明できる。

## 4章　順次処理・分岐・繰り返し〔T04〕

Sequenceは順番の明確な処理に向きます。Flowchartは分岐関係を図で整理できます。Ifは真偽による分岐、Switchは一つの値による分岐です。For Eachは集合の各要素、Whileは条件を先に調べる繰り返し、Do Whileは処理後に条件を調べる繰り返しです。

### 演習A：条件分岐

Int32変数 `amount` を作り、1000を代入します。Ifの条件に `amount >= 1000` を設定し、Thenに `"対象"`、Elseに `"対象外"` のWrite Lineを配置します。入力999・1000・1001で、それぞれ「対象外・対象・対象」を確認します。

### 演習B：集合の繰り返し

String配列 `names` に `New String(){"A", "B", "C"}` を代入します。For Eachでnamesを回し、要素の型をStringとして各値を出力します。期待はA、B、Cの順です。空配列に変え、要素処理が0回になることも確認します。

### 演習C：前判定と後判定

Int32変数 `counter` を0にします。Whileで `counter < 3` の間、counterを出力してから1増やします。期待出力は0、1、2です。開始値を3にすると0回です。同じ開始値3・同じ条件のDo Whileでは、本体が先に1回動くことを確認します。

Switchは文字列 `status` を対象にし、「New」「Done」とDefaultに異なる出力を置きます。未知の値がDefaultへ進むことを検証します。

**確認：**「処理を最低1回実行してから継続を判断したいときは？」  
**解説：**Do While。Whileは最初の条件がFalseなら本体を実行しない。  
**完了：**通常値・境界値・0件で結果を予測し、繰り返しが終わる理由を説明できる。

## 5章　文字列・日付・正規表現〔T05〕

文字列操作は、余分な空白を除く、部分を取り出す、区切る、置換する処理です。表示上の文字列と計算用の数値を区別します。日付を文字列として比べると形式次第で誤判定するため、必要な場合はDateTimeへ変換します。

**演習：**String変数textに `"  A-001  "` を入れ、`text.Trim()` で `A-001`、さらに `.Replace("-", "")` で `A001` を確認する。文字位置は0から始まる。 `"A,B,C".Split(","c)` で3要素を取り出す。日付は `DateTime.ParseExact("2026/10/09", "yyyy/MM/dd", System.Globalization.CultureInfo.InvariantCulture)` を試し、不正日付を別に試す。正規表現 `\d+` で `Order123` の数字部分を抽出する。

**確認：**「空白除去後に数値化すれば、どんな入力でも成功する？」  
**解説：**文字や桁あふれなどで失敗する。ParseとTryParseの使い分けを調べ、失敗時の処理を決める。  
**完了：**正常文字・空文字・不正日付の扱いと、変換失敗の記録を残した。

## 6章　配列・List・Dictionary〔T06〕

Array（配列）は作成した長さの要素を扱います。Listは要素の追加・削除を行う集合です。Dictionaryはキーと値の組を扱います。名前から住所を探すような処理では、キーによる参照が役立ちます。

**演習：**StringのListにA・Bを追加し、追加後のCountと各要素を出す。Dictionary(Of String, Int32)で `"A"` に10を対応させ、キーによる参照を行う。存在しないキーはContainsKeyなどで確認する。同じキーをAddした場合と、キーの値を更新した場合の違いを検証する。

**確認：**「同じキーにAddすれば既存の値が必ず上書きされる？」  
**解説：**DictionaryのAddは既存キーで例外になる。追加と更新を区別する。  
**完了：**各集合を選ぶ理由と、空集合・存在しないキーの扱いを説明した。

## 7章　DataTable〔T07〕

DataTableは行と列を持つメモリ上の表です。Excelファイル自体ではありません。DataRowは一つの行です。列には名前と型があり、文字列の「100」と数値100を区別します。欠損値DBNullと空文字も同じではありません。

**演習：**Build Data TableなどでID（String）・Amount（Int32）の表を作り、A/100、B/200、C/0を追加する。For Each Row in Data TableでAmountを合計し、300を確認する。Amountが100以上の行を抽出し2件になることを確認する。0行・列不足・欠損値を別ケースとして記録する。結合演習では2つの表を共通IDで対応させ、未一致IDをどう扱うか決める。

**確認：**「ヘッダーがあるExcelを読んだら、DataTableの列型は必ず数値型になる？」  
**解説：**読み取り方法や内容による。型を確認し、必要なら変換する。  
**完了：**抽出件数・合計・結合結果が期待値と一致し、欠損の扱いを説明できる。

## 8章　UI自動化・セレクター・待機〔T08〕

UI自動化では、対象アプリ・要素・操作・成功条件を分けて考えます。Selectorは属性を使って要素を指定します。Strict/Fuzzy、画像、Computer Visionなどの指定方法は、利用できる情報とパッケージに応じて選びます。XPath経験は属性の安定性を考える際に役立ちますが、UiPathのセレクター構文はXPathと同一ではありません。

固定のDelayを増やすだけでなく、要素の出現・状態・画面結果を待ちます。タイムアウトは「何秒で失敗扱いにするか」の設計です。入力モードも、対象アプリへの対応とバックグラウンド実行の可否を確認します。

**演習：**Use Application/Browserで練習ページを開き、Type Intoで入力、Clickで実行、Get Textで結果を取得する。対象指定を検証し、動的属性があれば安定属性に見直す。Check App State等を使い、結果表示を確認してから次へ進む。ページを閉じた場合と表示を遅らせた場合を試す。

**確認：**「いつも動くように10秒待てば待機設計は完成？」  
**解説：**応答が遅いと失敗し、速いと時間を浪費する。成功条件と上限時間を定義する。  
**完了：**対象指定の理由、待機条件、失敗時のログを残した。

## 9章　デバッグ・例外・ログ〔T09〕

Breakpointで止めて変数を確認し、Step Into/Overなどで動きを追います。例外処理は失敗を隠す機能ではなく、原因を残して処理の継続・中断・再試行を選ぶ仕組みです。

Try Catchは例外を扱い、Throwは例外を発生させ、RethrowはCatch内で受けた例外を再び上位へ渡します。Finallyは後片付けに使います。ログには処理名・対象ID・段階・結果を残し、パスワードなどの秘密情報は出しません。

Retry Scopeは条件が満たされない場合やエラー時の再試行に使えます。再試行の上限と間隔を設定し、書き込みが重複しないかを確認します。業務上の不正入力を、再試行するだけで直そうとしません。

**演習：**存在しないファイルを読む処理をTry Catchで扱う。CatchでIDと例外情報をログに残し、必要ならRethrowする。ブレークポイントでファイルパスを確認する。一時的失敗の再試行は別ワークフローで検証し、試行回数を数える。

**確認：**「例外をCatchして何も書かなければ正常終了としてよい？」  
**解説：**失敗が見えなくなる。期待結果を満たしたかを確認して結果を判定する。  
**完了：**正常・不正入力・一時的失敗を区別し、停止理由をログから追える。

**確認：**「Excel関連アクティビティは全てExcel未導入でも同じように動く？」  
**解説：**方式と機能による。使用アクティビティの前提を公式資料で確認する。  
**完了：**読み書き結果、依存条件、除外理由をREADMEに記録した。

## 11章　ファイル・フォルダーと実習A〔T11〜T12〕

相対パスは基準位置からの指定です。PC固有のユーザーパスを減らすと移動しやすくなりますが、基準位置が違えば違うファイルを指します。プロジェクトの基準ディレクトリを明記し、必要ならPath.Combineでパスを組み立てます。

**実習Aの仕様：**inputの架空CSV/Excelを読み、重複・欠損を検出してoutputに整形結果、logsに処理結果を出す。処理済みファイルの扱いはarchiveへ移すか、その場に残して処理済み記録で判定するかを選ぶ。

**検証ケース：**通常3件／入力0件／同名出力あり／列不足／出力先なし／同じ入力で2回実行。既存出力を無条件に上書きせず、仕様として決めた結果と比較する。

**確認：**「相対パスなら、どこから起動しても必ず同じファイルを読む？」  
**解説：**基準位置による。起動条件を変えて確かめる。  
**完了：**別の作業フォルダーに複製して再現でき、各検証の期待結果と実結果を保存した。

## 12章　メール〔T13・T16〕

**演習：**まず自作のダミー本文と添付ファイルを処理し、件名・送信者・添付の扱いを整理する。実接続は自分のテスト用アカウントで、受信・下書き作成などから始める。送信する場合は自分宛てのみとし、重複送信防止を確認する。

**確認：**「ダミーEMLを解析できれば、Microsoft 365の認証も実習済み？」  
**解説：**別の技能。接続未検証と明記する。  
**完了：**方式・認証・送信防止策を説明し、実接続と模擬処理を区別して記録した。

## 13章　PDF・OCR〔T14・T16〕

テキストを含むPDFと、スキャン画像だけのPDFでは抽出方法が異なります。OCRは画像の文字を認識しますが、誤読があるため桁数・書式・合計などで検証します。

**演習：**架空請求書をテキスト版と画像版で用意し、請求書番号・日付・金額を抽出する。Read PDF TextとOCRを使う方式を比較する。OCRが利用できない場合は認識結果のダミー文字列で後処理を練習し、OCR自体は未実習とする。

**確認：**「抽出文字が空なら、PDFに内容がない？」  
**解説：**画像PDFや抽出条件の可能性がある。PDFの性質を確認する。  
**完了：**抽出方式を選ぶ理由と、誤読・欠損を人へ回す条件を記録した。

## 14章　API・HTTP・JSON〔T15〕

APIは画面操作を介さず、決められた形式でシステムと情報をやり取りする入口です。HTTPのメソッド、応答コード、ヘッダー、本文を分けます。200台は成功系、400台は要求や権限などの問題、500台はサーバー側の問題の目安ですが、詳細はサービス仕様で判断します。

**演習：**ローカルのJSON `{"id":"A","amount":100}` をデシリアライズし、値を取り出す。HTTP Requestを使う場合は自分のローカルテストサービスなどを対象にし、成功・認証失敗・タイムアウトを試す。ファイル解析のみならHTTP接続は未実習と記録する。

**確認：**「HTTP 200なら業務処理も必ず成功？」  
**解説：**本文に業務エラーが入るAPIもある。応答コードと本文の仕様を確認する。  
**完了：**接続・認証・解析・業務判定を区別して説明できる。

## 15章　Object Repositoryと実習B〔T17〜T19〕

Object RepositoryはUI要素の定義を整理して再利用する仕組みです。対象が変わったときの修正箇所を減らす狙いがあります。画面名・要素名と用途を揃え、対象アプリの変更後は再検証します。

**実習Bの仕様：**架空ExcelのID・Name・Amountを練習フォームへ入力し、登録結果を回収する。登録済みIDを確認し、同じIDは仕様に従ってスキップまたは更新する。処理済み判定は、クリック成功だけでなく登録結果で確認する。

**検証ケース：**通常入力／空欄／重複ID／表示遅延／途中停止／再実行。書き込み成功直後に停止しても、再実行で二重登録しない仕組みを考える。UI部品をRepositoryへ整理し、再利用する。

**確認：**「登録ボタンをクリックできたら処理済みと記録してよい？」  
**解説：**登録結果を確認してから記録する。クリック後にエラーになる可能性がある。  
**完了：**登録結果と入力データが一致し、再実行でも重複しない。

## 16章　RPA Testingと中間診断〔T19〜T20〕

テストは、入力に対する期待結果と実結果を比べる活動です。データ駆動テストは入力と期待値の組を変えて同じ処理を確認し、モックは外部依存を置き換えて狙った条件を作ります。モックを通過しても、実サービスとの連携が確認できたわけではありません。

**演習：**実習A/Bに入力ケースと期待値の表を作る。利用できるテスト機能で正常・境界・異常系を検証する。テスト機能を利用できない場合は手動記録で代替し、機能未実習を明記する。中間診断では各章の問いを資料なしで説明する。

**確認：**「動いた画面のスクリーンショットだけでテスト完了？」  
**解説：**期待値と比較し、件数・金額・副作用も確認する。  
**完了：**失敗が分かる検証基準を用意し、実習と説明の弱点を分類した。

## 17章　Gitとレビュー〔T01・T26・T43〕

Gitは変更履歴を保存します。commitはローカルの履歴、pushはリモートへの送信です。branchは作業の分岐、mergeは変更の取り込みです。第三者が見る前提で、目的・前提・起動方法・入力例・期待結果をREADMEに書きます。

**演習：**既存リポジトリではなく学習用の場所で、初回commit、演習修正commit、branch、merge、リモートがある場合はpushを行う。競合は別々の変更を理解してから解消する。新規cloneまたは別フォルダーへの複製で再現確認する。

推奨構成：`README.md`、`project.json`、ワークフロー、`samples/`、`tests/`、`docs/`。実行用一時ファイルや秘密情報は除外する。第三者レビューは依頼する相手と共有範囲を自分で決め、コメントをIssueへ整理する。

**確認：**「commitしたら相手のGitHubにも必ず届いている？」  
**解説：**pushとリモート確認が必要。GitとGitHubは同じものではない。  
**完了：**変更理由を履歴で追え、READMEを見て再実行できる。

## 18章　Library・Template・Snippet〔T26〕

Libraryは再利用する処理部品を配布する仕組み、Templateは新規プロジェクトの土台、Snippetは再利用する処理断片です。共通化の前に入出力と例外の契約を決めます。特定のPCパスに依存した部品は再利用しにくくなります。

**演習：**実習Aの入力検証を小さなワークフローに分ける。可能な環境ではLibraryとして公開し、別プロジェクトから使用する。TemplateとSnippetも公式単元で作成・利用を確認する。使用版と依存パッケージを記録する。

**確認：**「共通化した処理は、入出力の仕様を変えても利用側へ影響しない？」  
**解説：**利用側が依存するため、版と互換性を考える。  
**完了：**3方式の用途を説明し、少なくとも再利用部品の入出力を検証した。

## 19章　Workflow Analyzer〔T12・T26〕

Workflow Analyzerは設定したルールに基づきワークフローを静的に分析します。命名・未使用データなどの指摘を確認し、原因を理解して対処します。実行結果が正しいことを保証する道具ではありません。

**演習：**実習Aで分析を実行し、ルールID・内容・対処を記録する。修正前後で比較し、必要な例外は理由を残す。Validateと実行テストも別に行う。

**確認：**「Analyzerの警告が0なら業務結果も正しい？」  
**解説：**静的な検査と、入力を使った動作検証は別。両方必要。  
**完了：**主な指摘を説明し、対応・保留の理由が残っている。

## 20章　Orchestratorの構成〔T21〕

| 用語 | 日本語での理解 |
|---|---|
| Tenant | 管理上の区分 |
| Folder | 資源や権限を整理する単位 |
| Machine | 実行環境に関する登録・構成 |
| Package | 公開した処理の配布物 |
| Process | 実行対象として設定された処理 |
| Job | 処理を実行した一つの単位 |

**演習：**Studioからの公開、PackageとProcess、実行後のJobの関係を図または文章で整理する。利用可能なら練習プロジェクトを公開し、実行結果を確認する。権限不足・ライセンス不足で試せない操作は区別して記録する。

**確認：**「同じProcessを3回実行した場合、Jobも一つ？」  
**解説：**実行ごとにJobとして扱われる。処理の定義と実行の履歴を分ける。  
**完了：**開発→公開→実行設定→実行結果の流れと必要権限を説明できる。

## 21章　Assets・Queues・Triggers〔T22〕

Assetは設定値や資格情報などを管理するための資源、Queueは処理する項目を管理する資源、Triggerは開始条件を設定する仕組みです。設定、仕事の一覧、開始条件を混同しません。

**演習：**利用可能なら設定値Assetを取得する。Queueに架空注文を追加し、取得して結果を記録する。再試行は例外種別とQueue設定を確認する。業務上のデータ不備は、同じ入力を繰り返しても直らない場合がある。時刻・タイムゾーンを確認してTriggerの動作を説明する。無人実行が利用できない場合は設定と流れの理解を記録する。

**確認：**「Queueの項目は、設定したら必ず全ての失敗が自動で再試行される？」  
**解説：**設定・例外種別・処理結果による。Application ExceptionとBusiness Exceptionを区別する。  
**完了：**各資源の用途を説明し、実習した操作と未実習の操作を分けた。

## 22章　Integration Service〔T23〕

Connectorは外部サービスへ接続する仕組み、Connectionは認証等を含む接続設定、Triggerは対応するイベントなどを開始条件として扱います。どのサービス・機能・権限が提供されるかを確認します。UIのクリックを自動化する方式と接続方式の違いを考えます。

**演習：**一つの対応サービスで必要な権限と接続の流れを調べる。自分のテスト環境で利用可能なら接続し、取得処理を試す。利用不可なら公式単元でConnector・Connection・Triggerの関係を説明する。

**確認：**「Connectorがあるなら、認証や権限の設定は不要？」  
**解説：**接続・権限・対応操作を確認する必要がある。  
**完了：**接続方式の選択理由、制約、認証情報の扱いを説明できる。

## 23章　実装工程と引継ぎ〔T23・T44〕

業務理解→要件整理→設計→開発→テスト→配布→運用の順に、何を決めるかを整理します。PDDは業務の手順やルールを説明する文書、SDDは自動化の実装設計を説明する文書です。例外や運用担当、復旧方法まで考えます。

**演習：**実習A/Bそれぞれについて、業務の入力・出力・判断・例外を1ページ相当で書く。続けて処理構成・再実行・ログ・依存関係・復旧を設計メモにする。「正常に動く」だけでなく、誰が失敗を見てどう再開するかを説明する。

**確認：**「実装したXAMLだけを渡せば引継ぎは十分？」  
**解説：**環境、操作、期待結果、制約、復旧が必要。レビューする人が再現できる状態を作る。  
**完了：**自動化の目的と例外対応を3分程度で説明でき、未経験・未実習の範囲も明記した。
