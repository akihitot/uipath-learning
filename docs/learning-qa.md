## Q1：なぜ入力後にカウントを増やす？

**質問：** カウントのタイミングは入力後？ Do Whileの条件の後ではない？

**答え：** 今回数えるのは「入力ダイアログを終えた回数」。入力直後に増やし、その更新済みの値で繰り返すか判断する。

現在の実習の順番：

1. 入力ダイアログ → 結果を `userName` に保存。
2. 代入：`attemptCount = attemptCount + 1`。
3. If：未入力なら案内、名前があればあいさつ。
4. Do Whileの条件：`String.IsNullOrWhiteSpace(userName) AndAlso attemptCount < 3`。
5. 両方Trueなら手順1へ。Falseならループを抜ける。
6. ループ後のIf：まだ未入力なら回数制限による終了案内。

| 入力後の回数 | 空欄の場合の判定 | 結果 |
|---|---|---|
| 1 | True AndAlso True | 再入力 |
| 2 | True AndAlso True | 再入力 |
| 3 | True AndAlso False | 終了 |
| 任意の回数で名前あり | False | 終了 |

**置き場所の違い：**

- 入力直後：入力完了の回数を数える。今回の配置。
- ループ内のIfの後・条件判定前：今回の処理では同じ結果。ただし後にIf内で回数を表示するなら、増やす順番に注意。
- 入力直前：開始した試行の回数を数える。入力中に失敗した場合の意味が異なる。
- **Do While全体の外・下：ループを抜けてから1回だけ動くため、回数制限には使えない。**

`attemptCount` はInt32、既定値は `0`、スコープはループとその後の判定を含む範囲。
確認するケース：スペースだけを3回、1回空欄の後に名前、3回目に名前。3回目に名前があれば成功扱いで、回数制限の案内を出さない。
キャンセル時の終了方法は、今回の実習にはまだ実装していない。

## Q2：WhileとDo Whileの使い分けは？

| UiPathアクティビティ | 条件を確認する時点 | 最少実行回数 |
|---|---|---|
| While | 本文の前 | 0回 |
| Do While | 本文の後 | 1回 |

Whileは「処理する対象があるなら実行」。Do Whileは「まず実行し、その結果で続けるか判断」。
今回の名前入力は必ず1回入力してほしいため、Do Whileが意図に合う。

**観察したこと：** WhileでuserNameの既定値に名前を入れると、空欄条件が最初からFalseになり、入力ダイアログもIfも動かず終了した。これは正常な動作。

VB.NET/VBAのコードでは、`Do While 条件 ... Loop` は前判定、`Do ... Loop While 条件` は後判定。UiPathのDo Whileは後判定。

## Q3：既定値を入れたのに入力結果で変わるのは？

既定値は変数の初期値であり、固定値ではない。

例：開始時「昭人」 → 入力ダイアログで「太郎」を入力してOK → 出力先userNameが「太郎」に更新 → 後続処理は「太郎」を使う。

変数の既定値と、入力画面にあらかじめ表示する文字は別の設定。出力先にuserNameを指定しただけでは、その既定値が入力欄へ表示されるわけではない。

## Q4：同じ空欄チェックが2つあるのは？

ループ条件は「もう一度実行するか」、本文内のIfは「どの案内を表示するか」を判断する。
同じ式でも役割と実行タイミングが違う。判断の重複だけで誤りとはいえない。

図でループ開始・終端の専用記号を使うと、ループ条件が開始記号に含まれるため、ひし形はIfの1つだけになる。判定の回数が減ったわけではない。

Flowchartで「入力 → 空欄判定 → 未入力案内 → 入力へ戻る／あいさつ → 終了」と接続すれば、条件判断1か所でも組み立てられる。

## Q5：Object型なのに文字を連結できないのは？

Objectは文字・数値などの値を受け取れるが、そのままどの演算にも使えるという意味ではない。
今回のメッセージボックス入力欄から作った変数はObject型になった。Option Strict Onでは、Objectのまま `&` を使う式が型エラーになった。

- 名前など文字と分かっている値：String型で作る。
- 整数の回数：Int32型で作る。
- 種類が一定でない値：Objectで受け取り、使うときに型を確認・変換する。

`userName.ToString()` で文字に変換できるが、中身がNothingなら呼び出しエラーになる。
変数の型を変えた後、既存の代入に古い型の設定が残ることがある。入力し直してもエラーが残る場合は、代入アクティビティを追加し直して確認する。

## Q6：引用符・数値への変換・大文字小文字

- `"昭人"`：文字そのもの。`昭人`：変数などの名前として解釈される。
- `userName`：変数の中身を使う。変数名に引用符は付けない。
- `"こんにちは、" & userName & "さん"`：String型の名前を文字とつなげる。
- VB.NETは識別子の大文字・小文字を区別しない。`username` と `userName` は同じ。ただし表記をそろえる。
- 整数の文字列を整数にする例：`Integer.Parse("123")`、`CInt("123")`。結果を保存する変数はInt32。
- `CInt` は小数の丸めも行うため、整数の文字列専用の解析と同じではない。変換できない入力や範囲外の値はエラーになる。任意のユーザー入力には、後でTryParseによる確認を学ぶ。

## Q7：デバッグ実行でもいい？

今回の実習では「ファイルをデバッグ」で動作確認できる。
ブレークポイントなどの停止条件がなければ通常は最後まで進む。エラーや停止設定によって途中で止まることはある。

「ファイル」は今開いているワークフロー、「プロジェクト」は設定されたエントリーポイントから実行する。

## Q8：Gitのステージングとは？

次のコミットに含める変更を選ぶ準備。

- 保存：編集したファイルをPCへ書き込む。
- ステージ：次のコミットに入れる変更を選ぶ。
- コミット：選んだ変更をPC内のGitへ履歴として保存する。
- プッシュ：コミットをGitHubへ送る。
- プル：GitHub側の変更をPCへ取り込む。

ステージ後の追加編集は自動でステージされない。追加分も含めるなら再度ステージする。
VS Codeの「変更の同期」は、取り込みと送信を行う。

## Q9：AndではなくAndAlsoを使う理由は？

日付：2026/10/11

**質問：** 両方の条件を満たすか調べるならAndでよいのでは？

Boolean条件のAndは左右の両方を評価する。AndAlsoは左がFalseなら右を評価しない（短絡評価）。

```vb
String.IsNullOrWhiteSpace(userName) AndAlso attemptCount < 3
```

名前が入力されていれば左がFalseなので、回数の確認を省略してループを終了する。今回の式はAndでも同じ判定結果になるが、AndAlsoは不要な処理を省き、右側の評価に前提条件がある場合のエラーを防ぐ。

```vb
userName IsNot Nothing AndAlso userName.Length > 0
```

左でNothingでないことを確認してから文字数を調べる。AndにするとNothingでも右を評価し、エラーになり得る。

右側も必ず評価したい理由がなければ、Boolean条件の組み合わせには基本的にAndAlsoを使う。副作用のある処理を右側に置く場合は、評価が省略されることにも注意する。

**今回の確認結果（本人報告）：** 空欄3回で終了、空欄の後に名前で成功、3回目に名前で成功、の3パターンを確認。PC上のワークフローのコミット・プッシュはこの記録時点では未確認。
